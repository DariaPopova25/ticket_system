# Ticket System

**Ticket System** — pet-проект на Django для создания и обработки заявок о проблемах на сайте.

Проект решает важную проблему: заявки не теряются, а проходят понятный путь от создания до завершения. Их удобно создавать, делегировать нужному специалисту и обсуждать в комментариях. Всегда можно понять, на каком этапе находится заявка по её статусу и насколько она важна по приоритету. Благодаря этому роли не путаются, зона ответственности понятна, а проблема доводится до решения.

## Ключевые особенности

- Основная бизнес-логика вынесена в сервисный слой, а часть базовой валидации находится в моделях. Благодаря этому web-часть опирается на уже готовую и понятную основу, а в будущем будет легче добавить API без дублирования логики и лишнего переписывания кода.

- Такой подход также упрощает развитие проекта: новую основную логику удобнее добавлять в сервисы, потому что правила работы заявки уже находятся в одном понятном месте.

- В проекте реализованы три роли: `client`, `manager` и `developer`. Благодаря этому действия с заявками чётко разделены по ответственности, и доступ к возможностям легко делегируется в зависимости от роли пользователя.

- В проекте есть понятный workflow заявки от создания до закрытия. Это показывает не только работу с кодом, но и понимание реального процесса: как заявка проходит этапы, кто отвечает за следующий шаг и как задача доводится до результата.

- Проект хорошо покрыт тестами. Тесты защищают ключевые сценарии в бизнес-логике, проверяют роли, ограничения доступа и важные правила работы с заявками.

- Для тестов используются `factory_boy` и удобные фабрики, благодаря которым проще и быстрее создавать тестовые данные.

- Настроен CI. Это уменьшает риск ошибок перед слиянием ветки в `main` и позволяет сразу видеть, проходят ли тесты и линтеры, даже без локальной проверки.

- Настроен Docker, поэтому проект удобно поднимать локально и проще подготавливать к деплою на хостинг.

- В проекте сделан простой и интуитивный web-интерфейс: заявку легко создать, открыть, отредактировать и обсудить в комментариях.

- Интерфейс также учитывает бизнес-логику:
  - кнопка редактирования скрыта для `client` и у закрытых заявок
  - ссылка на создание заявки доступна только `client`
  - в списке заявок есть пагинация
  - в комментариях реализовано удобное прокручиваемое окно
  - для менеджера в поле `assignee` доступны только пользователи с ролью `developer`
  - для `developer` в заявке доступны только разрешённые статусы
  - формы редактирования различаются для `developer` и `manager`

- PR описаны подробно и понятно. Можно открыть любой PR и быстро понять, что именно было сделано и как развивался проект по этапам.

- Созданы demo-пользователи, что упрощает просмотр проекта и позволяет сразу протестировать роли и основной сценарий работы.

## Что реализовано

### Основа

Реализованы три модели: кастомный `User`, `Ticket` и `Comment`, а также базовая валидация в моделях.

Добавлен сервисный слой — это основной предохранитель от ошибок при создании и изменении заявок. Именно в сервисах задаётся основная логика работы с заявками, ролями и правами доступа.

### Веб

Для `User` реализованы:
- регистрация
- логин
- выход

Для заявок и комментариев реализованы:
- список заявок с пагинацией
- детали заявки
- создание заявки по роли
- редактирование заявки по ролям
- комментирование открытых заявок

### Тесты

Используются `pytest` и `factory_boy`.

Реализованы:
- model tests
- service tests
- view tests

Тесты покрывают основную бизнес-логику проекта, роли, права доступа и ключевые сценарии работы.

За счёт этого проект хорошо защищён от ошибок в критичной логике.

Для ускорения тестов используется более быстрый способ хеширования паролей в тестовых настройках.

- создан Docker для хостинга
- проект успешно задеплоен на Render

Реализованы автоматические проверки через:

## Логика ролей

### Client

Клиент:
- создаёт заявку
- видит только свои заявки
- может писать комментарии только в своих заявках
- не может назначать исполнителя
- не может менять приоритет
- не может менять менеджерские и разработческие поля

### Manager

Менеджер:
- видит все заявки
- назначает разработчика
- меняет статус
- меняет приоритет
- заполняет `manager_notes`
- может комментировать заявки

### Developer

Разработчик:
- видит только назначенные ему заявки
- работает только со своими заявками
- меняет статус только в рамках разрешённых переходов
- заполняет `resolution_notes`
- может комментировать назначенные ему заявки

## Логика работы заявки

Стандартный сценарий:

`new -> pending_development -> in_progress -> pending_review -> done`

Также менеджер может отменить заявку:

`cancelled`

### Основные правила

- заявку создаёт только `client`
- менеджер назначает `developer`, выставляет приоритет и переводит заявку в работу
- разработчик не может работать с неназначенной ему заявкой
- разработчик не может выполнять менеджерские действия
- после статусов `done` и `cancelled` заявка становится закрытой и больше не редактируется и не комментируется
- назначить в `assignee` можно только пользователя с ролью `developer`
- для рабочих статусов обязательны `assignee` и `priority`
- разработчика можно снять только в статусе `new`

## Запуск через Docker

1. Клонировать репозиторий
2. Перейти в папку проекта
3. Создать `.env` на основе `.env.example`
4. Запустить проект
5. Открыть приложение в браузере

```bash
git clone https://github.com/DariaPopova25/ticket_system.git
cd ticket_system
cp .env.example .env
docker compose up --build
```

Приложение будет доступно по адресам:

- `http://127.0.0.1:8000`
- `http://localhost:8000`
